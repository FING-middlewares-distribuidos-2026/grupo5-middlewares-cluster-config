# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

GitOps configuration for the Kubernetes cluster that runs the "Twitter" project (grupo5). There is no application code here: the backend (`joacor7/twitter-api`) and frontend (`tomasrandom/grupo5-webapp`) images are built from the sibling repos `../grupo5-backend` and `../grupo5-webapp`. Changes reach the cluster only through Git: Flux watches `main` of `github.com/TomasRandoM/middlewares-cluster-config` (GitRepository interval 1m) and applies `./manifests` with `prune: true`. Work goes through PRs to `main`; merging is deploying.

## How Flux applies things

- `manifests/` has **no root `kustomization.yaml`**, so Flux auto-generates one that includes every YAML file under it recursively (including `manifests/dashboards/`). Adding a file there deploys it; deleting a file deletes its resources (prune).
- `manifests/flux-system/` is Flux's own bootstrap (`gotk-*.yaml`, marked "generated by flux, DO NOT EDIT").
- `infrastructure/` is **not** applied directly. It is reached only through the Flux `Kustomization` CRs in `manifests/metallb.yaml`: `metallb` (controller) then `metallb-config` (`dependsOn`, so the CRDs exist before the `IPAddressPool`/`L2Advertisement`).
- Third-party components are `HelmRepository` + `HelmRelease` pairs in the same file, mostly with the release in `flux-system` and `targetNamespace` set (e.g. `monitoring`). Chart versions are pinned; config lives in `spec.values`.

## Cluster layout

- **`twitter` namespace** — `twitter-backend.yaml` (Spring Boot on Cassandra + S3, HPA 1–5 replicas, so the Deployment intentionally omits `replicas`) and `twitter-frontend.yaml`. Both are `LoadBalancer` Services with fixed MetalLB IPs from `twitter-pool` (`10.66.51.51` backend, `10.66.51.52` frontend; pool only serves the `twitter` namespace, `autoAssign: false`). Changing the frontend IP also requires updating `CORS_ALLOWED_ORIGINS` (ConfigMap and the matching pod annotation) in the backend.
- Image updates are done by editing the image tag directly (commits like "Update front image").
- Backend metrics come from an OpenTelemetry Java agent injected via an initContainer (port 9464, no app code changes); `monitoring-targets.yaml` scrapes it.
- **Data stores** — Cassandra via `cass-operator.yaml` + `cassandra-cluster.yaml` (`CassandraDatacenter dc1`, service `clustercassandra-dc1-service.cassandra`); SeaweedFS (`seaweedfs.yaml`) provides the S3 endpoint `seaweedfs-s3.seaweedfs:8333`.
- **Nodes** — `grupo5-1` is the control plane; `grupo5-2..5` are `nodegroup=weak` (2 vCPU / 4 GiB, run Cassandra); `grupo5-6` and `grupo5-7` are `nodegroup=strong` (4 vCPU / 8 GiB). `grupo5-6` is general purpose (no taint). `grupo5-7` is reserved for CI: label `ci=true` + taint `ci=true:NoSchedule`, both set by hand, so only DaemonSets and ARC runners land there.
- **CI runners** — `arc-runners.yaml`: Actions Runner Controller (controller in `arc-systems`, scale sets `grupo5-mobile` and `grupo5-webapp` in `arc-runners`) runs the `checks` job of grupo5-mobile (`runs-on: grupo5-mobile`) and the `test`/`build` jobs of grupo5-webapp (`runs-on: grupo5-webapp`). Runner pods are ephemeral, pinned to `grupo5-7` via `nodeSelector`/toleration, and the `solo-internet` NetworkPolicy blocks them from reaching cluster services. See `docs/runner-ci.md`.
- Storage uses OpenStack Cinder CSI `StorageClass`es with `reclaimPolicy: Retain`, one per component, defined in that component's file.

## Monitoring stack (`monitoring` namespace)

- `prometheus.yaml`: kube-prometheus-stack (Prometheus + Alertmanager). Its bundled Grafana is not used; Grafana is a separate release in `grafana.yaml` with Prometheus/Loki/Alertmanager datasources.
- `loki.yaml` + `alloy.yaml` (DaemonSet log shipper) for logs; `blackbox-exporter.yaml` for HTTP/TCP probes.
- `monitoring-targets.yaml`: all extra `ServiceMonitor`/`PodMonitor`/`Probe` objects. They all live in `monitoring` and point elsewhere via `namespaceSelector`. Many have `metricRelabelings` dropping series to keep Prometheus memory down — preserve that intent when adding targets.
- `monitoring-alerts.yaml`: project `PrometheusRule`. Only alerts labelled `notificar: telegram` (plus the specific routes in `alertmanager.config` in `prometheus.yaml`) go to Telegram; everything else is visible only in Grafana.
- Alert delivery: Alertmanager → webhook receiver `bot` → `alertas-telegram.yaml` (a stdlib-only Python bot embedded in a ConfigMap, with silence buttons; the daily `Watchdog` becomes a summary). `telegram-directo` is the fallback. Editing `bot.py` does not restart the pod — bump the `alertas-telegram/version` pod annotation. The Deployment must stay `Recreate`/1 replica (Telegram allows a single `getUpdates` consumer).
- Dashboards: ConfigMaps in `manifests/dashboards/` labelled `grafana_dashboard: "1"` with a `grafana_folder` annotation, loaded by the Grafana sidecar. They are large generated JSON (`proyecto.yaml` says "Generado por un script"; the script is not in this repo), so edit the embedded JSON carefully.

## Resource constraints

Nodes are tight on memory (nodes running Cassandra have ~1 GiB free). Requests are set to observed real usage, and Grafana/Prometheus use anti-affinity against Cassandra pods. Keep requests/limits realistic and avoid adding heavy components without checking headroom.

## Secrets (created by hand, never in Git)

- `twitter-backend-secrets` in `twitter` (consumed via `envFrom` by the backend).
- `ghcr-pull` in `twitter` (type `kubernetes.io/dockerconfigjson`): `imagePullSecrets` of the frontend and backend, whose images live in the org's GHCR and cannot be public. Classic PAT with `read:packages`; recreate it when the PAT is rotated.
- `arc-github-token` in `arc-runners` (key `github_token`): fine-grained PAT with Administration read/write on grupo5-mobile and grupo5-webapp, shared by both scale sets; recreate it when the PAT is rotated.
- `alertmanager-telegram` in `monitoring` (keys `bot-token`, `chat-id`), used by both Alertmanager and the bot; must exist before deploying.

## Validating changes

There is no CI or test suite. `kubectl` is available locally (`flux` CLI is not). Useful checks:

- `kubectl kustomize infrastructure/metallb/config` — render a kustomization.
- `kubectl apply --dry-run=client -f manifests/<file>.yaml` — schema/YAML sanity (CRD kinds need cluster access or `--dry-run=server`).
- With cluster access: `kubectl -n flux-system get kustomizations,helmreleases` to see reconciliation status after a merge.

## Conventions

- Comments in manifests are written in Spanish and explain *why* a non-default value was chosen; follow that style.
- Commit subjects are short, English or Spanish, describing the change (e.g. "Raise backend CPU request to 250m").
